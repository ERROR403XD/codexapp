> [!important] 最短结论
> 生产 CodexApp 始终通过 `systemctl start codexapp.service` 启动。不要手动运行 `node dist-cli/index.js`、`npx codexapp` 或复制某个旧 release 的启动命令。systemd 会自动使用当前生产 release，并继续使用 `/root/.codex` 中的登录、账号、会话和配置。

## 生产边界

| 对象 | 固定边界 | 说明 |
| --- | --- | --- |
| systemd 服务 | `codexapp.service` | 唯一正式启动入口 |
| 生产端口 | `5900` | 页面地址为 `http://192.168.50.46:5900/` |
| 生产 Codex home | `/root/.codex` | 保存生产登录、账号池、会话、配置、skills 和 memories |
| 版本选择 | systemd base unit 或 release drop-in | `systemctl start` 会自动使用当前选中的版本 |
| 候选测试环境 | `codexapp-multi-account-dev:59001` | 不是生产服务，重启后不得用它代替 5900 |

> [!warning] 不可操作项
> 普通重启后恢复不需要删除、替换或复制 `/root/.codex`。不得将 59001 的 Docker volume、`auth.json` 或账号池复制到生产。文档和命令输出中也不得展示认证文件内容。

## 正常启动流程

### 1. SSH 登录服务器

等待 VUbuntu 完成启动并恢复网络后，通过 SSH 或本机终端进入 `192.168.50.46`。以下命令需要 root 权限；非 root shell 应在 `systemctl` 命令前加 `sudo`。

### 2. 先检查是否已经自动启动

```bash
systemctl is-enabled codexapp.service
systemctl is-active codexapp.service
systemctl status codexapp.service --no-pager
```

当前 unit 已设为 `enabled`，因此服务器正常重启后应该自动启动。

- 如果返回 `enabled` 和 `active`：不需要再执行 `start`，直接进入“启动后验证”。
- 如果是 `inactive`：继续执行下一步。
- 如果是 `failed`：先执行“启动失败排查”，不要盲目循环重启。

### 3. 查看当前将要启动的版本

```bash
cd /home/Code/codexapp
./scripts/codexapp-release-switch.sh status
systemctl show codexapp.service -p FragmentPath -p DropInPaths -p ExecStart -p Environment
```

检查要点：

- `Environment` 必须包含 `CODEX_HOME=/root/.codex`。
- `active_release=base-unit` 表示尚在使用原始兜底部署。
- `active_release=.../codexapp-releases/.../dist-cli/index.js` 表示使用某一轮已激活 release。
- 两种结果都由 systemd 管理，不需要手工修改 `ExecStart`。

### 4. 手动启动 5900 生产服务

```bash
systemctl start codexapp.service
```

该命令不会创建新账号，不会从 59001 导入账号，也不需要重新执行 `prepare` 或 `activate`。

## 启动后验证

### 1. 检查 systemd 状态

```bash
systemctl is-active codexapp.service
systemctl status codexapp.service --no-pager
```

预期 `is-active` 返回 `active`，且状态中没有循环重启或立即退出。

### 2. 检查 5900 端口和首页

```bash
ss -ltnp | grep ':5900'
curl -fsS -o /dev/null -w 'HTTP %{http_code}\n' http://127.0.0.1:5900/
```

预期：

- 端口 5900 正在监听。
- 首页返回 `HTTP 200`。

HTTP 200 只证明 Web 服务启动，不代表账号一定可用。

### 3. 检查生产登录状态

```bash
codex login status
stat -c '%a %U:%G %n' /root/.codex /root/.codex/auth.json
```

正常情况下：

- `codex login status` 表示已使用 ChatGPT 登录。
- `/root/.codex` 权限为 `700`。
- `/root/.codex/auth.json` 权限为 `600`。

只检查存在性、权限和登录状态，不要使用 `cat` 查看 `auth.json`。

### 4. 在浏览器中验证

打开：

```text
http://192.168.50.46:5900/
```

检查：

- 项目、历史线程和当前工作区能正常读取。
- Accounts 中存在生产账号，预期账号为 active。
- 如果目标账号已 ready 但不是 active，在确认账号 identity 后手动点击“切换”。
- 发送一条无害测试消息，确认真实响应成功，而不是只看 ready 或配额。

## 可直接照抄的快速流程

```bash
# 1. 查看服务是否已自动启动
systemctl is-enabled codexapp.service
systemctl is-active codexapp.service

# 2. 仅在返回 inactive 时手动启动
systemctl start codexapp.service

# 3. 验证服务、版本选择和端口
systemctl is-active codexapp.service
cd /home/Code/codexapp

ss -ltnp | grep ':5900'

# 4. 只检查登录状态，不输出凭据内容

```

## 启动失败排查

### 情况 A：服务是 failed

先保留现场并查看本次开机日志：

```bash
systemctl status codexapp.service --no-pager
journalctl -u codexapp.service -b -n 150 --no-pager
systemctl show codexapp.service -p DropInPaths -p ExecStart -p Environment
```

根据日志处理明确原因后，再重置失败状态并启动：

```bash
systemctl reset-failed codexapp.service
systemctl start codexapp.service
```

不要在原因未明时连续执行 `restart`。

### 情况 B：5900 端口被其他进程占用

```bash
lsof -nP -iTCP:5900 -sTCP:LISTEN
```

先记录 PID、命令和工作目录，确认占用者后再决定处理方式。不要盲目 `kill -9`，也不要让 CodexApp 自动改用其他端口；生产入口必须保持 5900。

### 情况 C：当前 release 路径不存在

```bash
cd /home/Code/codexapp
./scripts/codexapp-release-switch.sh status
systemctl show codexapp.service -p DropInPaths -p ExecStart
```

不要手工猜测另一个 release 并改写 systemd drop-in。保留日志和现有 `/home/docker/codexapp-switch-state/transactions/`，然后按新旧版本交接手册中的回滚边界处理。如果服务无法进入 active，不要强行运行需要 active 服务前置的 `rollback` 命令，应先交由 Codex 根据事务快照制定定向恢复步骤。

### 情况 D：页面正常，但账号不可用

1. 执行 `codex login status`。
2. 在 Accounts 中确认目标账号 identity 和状态。
3. 如果账号 ready 但未 active，手动点击“切换”。
4. 如果明确显示需要重新认证，使用该账号的“重新认证”流程；不要删除整个 `/root/.codex`。
5. 再执行真实无害消息测试。

- 版本原则：永远启动 systemd service，让 base unit/release drop-in 选择当前生产版，不直接运行应用入口。
- 认证原则：保留 `/root/.codex`；不复制 59001 认证；账号 ready 但未 active 时手动点击“切换”。

- 未验证：本文未实际执行整机 reboot，因此实际开机恢复时间待下次维护窗口记录。
- 关键路径：`/etc/systemd/system/codexapp.service`、`/etc/systemd/system/codexapp.service.d/90-release-switch.conf`、`/root/.codex`、`/home/docker/codexapp-releases/`、`/home/Code/codexapp/scripts/codexapp-release-switch.sh`。
- 操作限制：不删除或展示认证文件；不手改 `ExecStart`；不盲目杀掉 5900 占用进程；不用 59001 替代生产。
